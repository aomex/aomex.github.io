# ETag

Для успешных GET/HEAD считается entity tag: если клиент шлёт If-None-Match и содержимое не менялось — **304**, меньше трафика. Подходит для полустатичных конфигов и сведений о версии; на сильно персонализированных списках выгода обычно мала.

```bash
pnpm add @aomex/etag
```

## Монтирование на весь WebApp

Повесьте `etag()` в `WebApp.mount`: успешные GET/HEAD сами получат ETag; при совпадении If-None-Match и неизменности — 304. В бизнесе по-прежнему `ctx.send`.

```typescript
import { etag } from '@aomex/etag';
import { routers, WebApp } from '@aomex/web';

const app = new WebApp({
  services,
  logger: services.logger,
  language: { mode: 'fixed', language: 'zh-CN' },
  proxyIP: { mode: 'detect' },
  mount: [ // [!code focus:4]
    etag(), // [!code highlight]
    routers('./src/routers'),
  ],
});
```

Бизнес по-прежнему `ctx.send(data)`; при совпадении и «свежести» middleware отдаёт 304 с пустым body.

Обычный WebMiddleware, новых полей на ctx нет. Эффект: первый ответ с ETag; повторный запрос с If-None-Match и совпадением → **304**. Если Etag уже есть, статус не 2xx или метод не GET/HEAD — обычно не переписывает.

::: tip
Если на всём сайте включена [обёртка тела ответа](/ru/web/envelope), оболочка переписывает body и внешний статус в 200; фреймворк **снимает исходный ETag**, чтобы дайджест не соответствовал содержимому до оболочки. Для условного кеша убедитесь, что дайджест считается после оболочки, или сделайте `skipEnvelope` на этом выходе.
:::

## Полустатичное API

Публичный конфиг, сведения о версии — GET, которые «почти не меняются»: достаточно повесить на весь сайт; бизнес как обычно ходит в БД и `send`:

```typescript
router.get('/api/config', {
  action: async (ctx) => {
    ctx.send(await loadPublicConfig());
  },
});
```

Когда JSON собирается динамически, но семантически достаточно 304, включите слабую проверку: `etag({ weak: true })` (по умолчанию сильная; для `ReadStream` часто слабая). Списки вроде «заказы пользователя» на весь сайт насильно не включайте.

## Статика + сжатие

Когда статический каталог и сжатие стоят рядом, ETag обычно ставят раньше, чтобы дайджест видел содержимое до финальной записи (ориентируйтесь на реальное поведение 304 / объёма):

```typescript
mount: [
  etag(), // [!code highlight]
  compress(),
  serveStatic({ root: './dist' }),
  routers('./src/routers'),
],
```

Локально отладка JSON часто «прячется» за 304 — временно не монтируйте или сделайте hard refresh; для проверки условных запросов снова включите:

```typescript
mount: [
  ...(process.env.NODE_ENV === 'production' ? [etag()] : []),
  routers('./src/routers'),
],
```

| Среда | Рекомендация |
| --- | --- |
| Прод | статику и полустатичные интерфейсы стоит включить; персонализированное API на весь сайт не обязательно |
| Локально | если 304 мешает отладке — временно снять или hard refresh |

При большом трафике кеш можно отдать CDN; in-app ETag нужен, когда вы сами хотите контролировать семантику 304. Если каждый ответ персональный, а ETag всё равно на весь сайт — CPU на дайджестах зря.
